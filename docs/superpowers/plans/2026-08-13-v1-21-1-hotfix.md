## Task 2: Add regression test for `UserPrefs` id-remap persistence

**Goal:** lock in the persistence contract that keeps id-remap alive across process kill. This is the sole reason `getIdRemap/setIdRemap` exist — the maps in `SyncManager` are re-populated from these on next launch.

**Files:**
- Create: `app/src/test/java/com/example/billiardtracker/data/prefs/IdRemapPersistTest.kt`

- [ ] **Step 1: Write the failing test file**

```kotlin
package com.example.billiardtracker.data.prefs

import androidx.datastore.preferences.core.PreferenceDataStoreFactory
import kotlinx.coroutines.runBlocking
import org.junit.After
import org.junit.Assert.assertEquals
import org.junit.Assert.assertNull
import org.junit.Before
import org.junit.Test
import java.io.File

/**
 * Persistent id-remap must survive process kill between successful
 * create_tournament (server 201 → in-memory tournamentIdRemap[localTid] = serverId)
 * and enqueue of the dependent child op (start_game) that still references localTid.
 * See SyncManager.persistRemap / loadPersistedRemap. Regression: v1.21.0 lost this
 * mapping on cold start and the child op sat in outbox forever (⏳ badge grew).
 */
class IdRemapPersistTest {
    private lateinit var prefsFile: File
    private lateinit var prefs: UserPrefs

    @Before
    fun setUp() {
        prefsFile = File(
            System.getProperty("java.io.tmpdir"),
            "idremap-test-${System.nanoTime()}.preferences_pb",
        )
        val ds = PreferenceDataStoreFactory.create(produceFile = { prefsFile })
        prefs = UserPrefs(ds)
    }

    @After
    fun tearDown() {
        prefsFile.delete()
    }

    @Test
    fun `default remap is null`() = runBlocking {
        assertNull(prefs.getIdRemap())
    }

    @Test
    fun `set then get returns the stored string`() = runBlocking {
        prefs.setIdRemap("t:-1:42,g:-7:99,p:-3:17")
        assertEquals("t:-1:42,g:-7:99,p:-3:17", prefs.getIdRemap())
    }

    @Test
    fun `empty string clears the entry (semantically null)`() = runBlocking {
        prefs.setIdRemap("t:-1:42")
        prefs.setIdRemap("")
        assertNull(prefs.getIdRemap())
    }

    @Test
    fun `null clears the entry`() = runBlocking {
        prefs.setIdRemap("t:-1:42")
        prefs.setIdRemap(null)
        assertNull(prefs.getIdRemap())
    }

    @Test
    fun `overwrite replaces prior mapping`() = runBlocking {
        prefs.setIdRemap("t:-1:42")
        prefs.setIdRemap("t:-2:55,g:-3:66")
        assertEquals("t:-2:55,g:-3:66", prefs.getIdRemap())
    }
}
```

## Task 6: [conditional] Fix «Партия окончена» if independent bug

**Only execute if Task 5 Step 3 fired.** Otherwise skip to Task 7.

**Goal:** patch the exact identified root cause. No speculative fixes.

**REQUIRED SUB-SKILL:** invoke `superpowers:systematic-debugging` for this task — the whole point of Task 5 was to gather evidence, not to jump to a fix.

**Files:** determined by which hypothesis Task 5 Step 3 confirms. Match one of these three:

**Hypothesis 1: RefereePanel stays on screen after tap**

Symptom: `currentGame.status` never flips to `"finished"` in the UI state.
- Look at `TournamentViewModel.finishGame()` (`app/src/main/java/com/example/billiardtracker/ui/screens/tournament/TournamentViewModel.kt:177-194`) — it calls `gameRepo.finishGame(...).onSuccess { refresh() }`. If `refresh()` runs before Room's `upsert` commits (transaction ordering race), the reloaded state still shows `status = "active"`.
- **Fix**: inside `onSuccess`, update `_ui.value` optimistically first (`currentGame = currentGame?.copy(status = "finished")`), then call `refresh()`. Test: unit-test `TournamentViewModel` with a fake `GameRepository` that returns success synchronously; assert the UI-state flip is immediate.

**Hypothesis 2: Game vanishes but no finished-row appears in "Партии"**

Symptom: local `Game` entity got `status = "finished"` but `refresh()` returns a list where that game is missing.
- Look at `GameRepository.finishGame()` (`app/src/main/java/com/example/billiardtracker/data/repo/GameRepository.kt:150-195`) — the `games.upsert(local.copy(status = "finished", ...))` at lines 166-172. If `winnerParticipantId` is null (2-player game with 0-0 tie), the `finishedGames.filter { it.status == "finished" }` in `TournamentScreen.kt:185` would still show it — so this hypothesis is unlikely unless there's a serialization bug in `Game.copy`.
- **Fix**: add a test in `app/src/test/java/com/example/billiardtracker/data/repo/GameRepositoryFinishTest.kt` using an in-memory Room DB; call `finishGame`, then `gameDao.getById(gid)` and assert `status = "finished"`.

**Hypothesis 3: Game finishes locally but ⏳ grows and never drops**

Symptom: after «Партия окончена», ⏳ badge increments but drain doesn't clear it.
- Look at `SyncManager.executeOne()` `"finish_game"` branch. This one uses `realGid` from the resolver — if `resolveGameId` returns the negative local id (no server-side mapping yet), the endpoint `api/tournaments/$tid/games/$gid/finish` becomes invalid.
- **Fix**: extend the bypass logic — for `finish_game`, if `realGid` is still negative, block (return null) until the parent `start_game` synced. Or (better) chain the multi-pass drain re-fetch to include finish_game deps. Test: add a scenario to `IdRemapPersistTest` — but this is likely already caught by the Task 4 smoke.

**Do NOT invent a 4th hypothesis without evidence** — return to Task 5 to gather more.
